# AI-Talk 설계 문서

상태: 4판 (2026-11-17). 첫 버전을 만들고, 써 보신 뒤 주신 의견을 반영했습니다([16번](#16-써-본-뒤-바꾼-것)). 만든 것, 확인한 것, 아직 안 된 것은 [15번](#15-첫-버전에서-만든-것과-남은-것)에 있습니다. 실행 방법은 [README](../README.md)에 있습니다.

2판에서 바뀐 것: 13번 질문에 주신 답을 반영했습니다. P-GPT는 대화 문맥을 API가 보관하는 방식(상태 유지)으로 바꾸고 자동 압축을 넣었습니다([8.4](#84-p-gpt-api가-문맥을-보관하는-방식), [8.5](#85-문맥이-넘칠-때-자동-압축)). GPT 모델은 6.0 이후만 쓰고 기본값을 정했습니다([7.3](#73-모델과-추론-노력)).

3판에서 바뀐 것: GPT 모델을 `gpt-6-luna`, `gpt-6.1-sol`, `gpt-6.1-terra` 세 가지로 정했습니다. 감정에 따라 움직이는 아바타를 넣었습니다([9.4](#94-모션-아바타)). Claude의 문맥 압축 방식을 바꿨습니다([8.5](#85-문맥이-넘칠-때-자동-압축)).

읽는 순서: 급하면 [1. 무엇을 만드나](#1-무엇을-만드나)와 [13. 정한 것과 남은 질문](#13-정한-것과-남은-질문)만 보셔도 됩니다.

표시 규칙: 요청하신 내용은 그대로 적었고, 제가 덧붙인 것은 **(제안)**, 아직 확인하지 못한 것은 **(미검증)**으로 표시했습니다.

## 1. 무엇을 만드나

주제를 하나 던지면 AI 참가자 여러 명이 실제 토론처럼 대화하는 프로그램입니다. 사용자는 그 토론을 지켜보는 관객입니다.

핵심 목표는 세 가지입니다.

1. **실제 같은 토론.** 발언 순서가 정해진 대로만 돌지 않고, 두 사람이 맞붙다가 다른 사람이 끼어드는 흐름이 자연스럽게 나옵니다. 말하는 속도와 발언 사이의 뜸도 사람과 비슷합니다.
2. **싸게 오래.** 기본은 모델 하나로 전원을 돌려 입력 캐시 할인을 받습니다. 원하면 화자마다 모델과 추론 노력을 따로 정해, 성능이 다른 AI가 어떻게 다르게 말하는지 관찰할 수 있습니다.
3. **보기 좋은 화면.** 참고 사이트(wowf.io)의 어두운 바탕과 금색 장식을 따르고, 모션으로 누가 말하고 누가 말하고 싶어 하는지 한눈에 보이게 합니다.

하지 않는 것: 음성(읽어 주기), 여러 사용자가 함께 쓰는 서버, 로그인. 내 PC에서 혼자 쓰는 프로그램입니다.

## 2. 사용 흐름

```
① 주제 입력 ─ ② 자료 붙이기(선택) ─ ③ 참가자 구성 ─ ④ 진행 방식 설정 ─ ⑤ 토론 관람 ─ ⑥ 기록 저장·다시 보기
```

| 단계 | 사용자가 하는 일 | 프로그램이 하는 일 |
|---|---|---|
| ① 주제 | 주제를 한 줄에서 몇 문단까지 자유롭게 씁니다 | |
| ② 자료 | 문서를 올리거나 웹 주소를 붙입니다 (선택) | 문서는 글자를 뽑아 두고, 웹 주소는 진행자가 조사해 브리핑을 만듭니다 |
| ③ 참가자 | 인원을 정하고(2~10명), 자동 생성하거나 보관함에서 고릅니다 | 주제에 맞는 페르소나를 인원수만큼 만듭니다 |
| ④ 진행 | 진행 방식, 턴 수, 시간, 검색 허용 여부, 모델을 정합니다 | 기본값을 채워 두므로 그냥 시작해도 됩니다 |
| ⑤ 관람 | 지켜보다가 멈추거나, 속도를 바꾸거나, 끼어듭니다 | 토론을 진행하고 화면에 실시간으로 보여 줍니다 |
| ⑥ 기록 | 지난 토론을 다시 보거나 파일로 내보냅니다 | 토론이 끝나면 자동 저장합니다 |

## 3. 토론 엔진

### 3.1 등장하는 역할

| 역할 | 화면에 보이나 | 하는 일 |
|---|---|---|
| 참가자 (2~10명) | 보임 | 각자 페르소나대로 발언합니다 |
| 진행자 (0~1명) | 보임 | 개회, 발언권 정리, 화제 전환, 시간 안내, 마무리 정리. 웹 주소가 주어지면 조사도 맡습니다 |
| 연출자 | 안 보임 | 발언이 끝날 때마다 "다음에 누가 말할지"를 판단하는 내부 역할입니다 **(제안)** |

참가 인원 기본값은 4명입니다. 2~10명 사이에서 바꿀 수 있고, 5명이 넘으면 "발언 기회가 줄어든다"는 안내를 보여 줍니다. 진행자는 이 인원에 넣지 않고 따로 둡니다(확정).

### 3.2 진행 단계

```
준비(자료 조사) → 개회 → 모두발언 → 자유토론 → 마무리 발언 → 진행자 정리
```

- **준비**: 웹 주소가 있으면 진행자가 조사해 브리핑을 만듭니다. 자료가 없으면 건너뜁니다.
- **개회**: 진행자가 주제와 참가자를 소개합니다. 진행자를 껐으면 건너뜁니다.
- **모두발언**: 한 명씩 돌아가며 입장을 밝힙니다.
- **자유토론**: 상황에 따라 발언자가 바뀝니다. 아래 3.4에서 설명합니다.
- **마무리 발언**: 남은 턴이나 시간이 20% 아래로 내려가면, 진행자가 마무리를 알리고 한 명씩 마지막 발언을 합니다.
- **진행자 정리**: 합의된 점과 끝까지 갈린 점을 정리합니다.

### 3.3 진행 방식 세 가지

| 방식 | 설명 | 쓰임 |
|---|---|---|
| 순차 | 처음부터 끝까지 1→2→3→4 순서로 돕니다 | 모두가 같은 분량으로 말해야 할 때 |
| 자유 | 처음부터 상황에 따라 발언자가 바뀝니다 | 가장 실제 같은 흐름 |
| 혼합 (기본) | 모두발언은 순차, 그 뒤는 자유 | 방송 토론과 같은 구성 |

### 3.4 자유토론에서 다음 발언자를 정하는 법

요청하신 "1-2-3-2-3-4-2-3-1" 같은 흐름을 억지 규칙 없이 만들기 위한 구조입니다.

**발언이 하나 끝날 때마다** 연출자가 한 번 호출됩니다. 연출자는 지금까지의 토론을 읽고 참가자 전원에 대해 다음을 내놓습니다.

- **발언 의지** (0~10점): 지금 얼마나 말하고 싶은가
- **의도**: 반박 / 보충 / 질문 / 동의 / 화제 전환 가운데 하나
- **상대**: 누구의 말에 반응하려는가
- **감정**: 방금 발언을 들은 지금의 기분. 평온 / 수긍 / 못마땅 / 격앙 / 궁금 / 놀람 / 웃음 / 고민 가운데 하나. 아바타가 이 감정대로 움직입니다([9.4](#94-모션-아바타))
- 진행자가 나서야 하는지 여부와 이유

이 결과에 코드가 다음 규칙을 더해 한 명을 고릅니다.

| 규칙 | 효과 |
|---|---|
| 방금 말한 사람은 감점 | 같은 사람이 연달아 말하는 일을 줄입니다 |
| 방금 지목받거나 질문받은 사람은 가산 | 질문에는 답이 따라옵니다 |
| 오래 말하지 않은 사람은 조금씩 가산 | 두 사람이 주도하다가도 다른 사람이 끼어들게 됩니다 |
| 약간의 무작위 | 매번 같은 패턴이 되지 않습니다 |
| 진행자 개입 조건 | 같은 주장이 되풀이될 때, 한두 명이 너무 오래 독점할 때, 턴이나 시간의 절반·80% 지점일 때 진행자가 나섭니다 |

이렇게 하면 서로에게 발언 의지가 높은 두 사람이 한동안 주고받다가, 조용하던 사람의 점수가 쌓여 끼어드는 흐름이 저절로 생깁니다. 규칙의 세기(예: 침묵 가산을 얼마나 줄지)는 설정에서 조절할 수 있게 합니다.

발언 의지 점수는 화면에도 씁니다. 참가자 타일 아래 게이지로 보여 주어 "지금 누가 말하고 싶어 하는지"가 보입니다.

발언자에게는 연출자의 판단이 지시문으로 전달됩니다. 예: "○○의 방금 주장에 반박하세요. 2~4문장."

### 3.5 끼어들기

발언 의지가 특히 높고 의도가 반박이면 **끼어들기**로 처리합니다. 앞 발언을 실제로 끊습니다(확정).

- 앞 사람의 발언을 문장 끝에서 끊습니다. 화면에는 말줄임(—)으로 표시하고, 기록에도 끊긴 데까지만 남습니다.
- 끼어든 사람은 뜸 없이 바로, 짧게 말합니다.
- 끼어들기가 너무 잦지 않도록 최소 간격을 둡니다. 설정에서 끌 수 있습니다.

가능한 이유: 화면에 글자가 나오는 속도가 AI가 글을 만드는 속도보다 느립니다. 그래서 앞 발언이 화면에 다 나오기 전에 다음 판단이 이미 끝나 있습니다.

### 3.6 끝나는 조건

- **턴 수 제한**: 기본 30턴 (진행자 발언 포함).
- **시간 제한**: 기본 10분.
- 둘 중 먼저 닿는 쪽에서 마무리 단계로 넘어갑니다. 한쪽만 쓰도록 끌 수도 있습니다.

시간은 **토론 시계**로 잽니다. 토론 시계는 발언 글자 수를 기준 속도로 환산한 발화 시간에 발언 사이의 뜸을 더한 값입니다. 그래서 "즉시 출력" 모드로 봐도 10분짜리 토론의 분량은 같습니다.

### 3.7 관람 중에 할 수 있는 일 (제안)

요청에는 없었지만 필요해 보여 넣었습니다.

- 일시정지 / 이어 하기 / 지금 끝내기 (끝내면 바로 마무리 단계로 갑니다)
- 출력 속도 바꾸기, 지금 발언 건너뛰기
- 진행자에게 지시하기: "이제 비용 문제로 넘어가 주세요"
- 청중 질문 던지기: 진행자가 받아서 참가자에게 묻습니다

## 4. 실제처럼 보이게 하는 장치

| 장치 | 기본 동작 | 설정 |
|---|---|---|
| 출력 속도 | 어절 단위로 나오고, 쉼표와 문장 끝에서 잠깐 멈춥니다 | 느리게 / 보통(기본) / 빠르게 / 즉시 |
| 발언 사이 뜸 | 의도에 따라 다릅니다. 끼어들기는 거의 없음, 반박은 짧게, 화제 전환과 진행자 발언은 길게 | 뜸 길이 배율, 끄기 |
| 발언 준비 표시 | 다음 발언자의 타일이 먼저 밝아지고 숨 쉬듯 움직입니다 | |
| 검색 중 표시 | 참가자가 자료를 찾는 동안 타일에 표시하고 검색어를 보여 줍니다 | |
| 미리 만들기 | 지금 발언이 화면에 나오는 동안 다음 발언을 미리 만들어 둡니다. AI 응답 대기 시간이 뜸 속에 숨습니다 | 한 턴만 앞서 만듭니다 |

"즉시" 모드는 뜸과 속도 조절을 모두 끄고, 만들어지는 대로 최대 속도로 보여 줍니다.

속도 조절은 서버가 맡습니다. 서버가 글을 다 받아 둔 뒤 정해진 박자로 화면에 내보냅니다. 이 내보낸 기록을 시간과 함께 저장하므로 지난 토론을 같은 박자로 다시 볼 수 있습니다.

## 5. 페르소나

### 5.1 구성

**인물**과 **이번 토론에서의 입장**을 나눕니다. 인물은 보관함에 두고 여러 토론에 다시 쓰고, 입장은 토론마다 주제에 맞춰 새로 만듭니다.

| 구분 | 항목 |
|---|---|
| 인물 (보관함에 저장) | 이름, 한 줄 소개(직함·배경), 전문 분야, 성격과 토론 스타일(공격적인지 신중한지, 논리·사례·감정 중 무엇에 기대는지), 말투와 말버릇, 말 길이 성향, 색, 아이콘, 태그 |
| 입장 (토론마다 생성) | 이 주제에서의 관점, 핵심 주장 2~3개, 양보할 수 있는 지점, 숨은 속내(선택) |
| 고급 설정 (선택) | 이 화자만 쓸 모델, 추론 노력 |

### 5.2 만드는 방법

- **자동 생성**: 주제와 인원수를 주면 AI가 한 번에 전원을 만듭니다. 구성 방침을 고를 수 있습니다: 찬반 균형 / 여러 이해관계자 / 전문가 패널 / 알아서.
- **보관함에서 선택**: 미리 만들어 둔 인물을 고릅니다. 입장만 주제에 맞춰 자동 생성합니다.
- **섞기**: 일부는 보관함에서 고르고 나머지 자리는 자동 생성으로 채웁니다.
- 만들어진 페르소나는 시작 전에 고치거나, 한 명만 다시 만들거나, 보관함에 저장할 수 있습니다.

자동 생성은 가상 인물만 만듭니다. 실존 인물의 이름으로 발언을 지어내는 일은 피합니다 **(제안)**.

### 5.3 관리 메뉴

- 카드 목록, 검색, 태그 필터
- 새로 만들기 / 고치기 / 복제
- "한 줄 설명으로 초안 만들기": 예) "원칙을 중시하는 30년 차 설비 엔지니어"라고 쓰면 AI가 나머지를 채웁니다
- 삭제: 휴지통 아이콘을 두 번 눌러야 지워집니다 (전역 지침의 삭제 규칙)
- 가져오기 / 내보내기 (JSON 파일). 집과 회사 PC 사이에 옮길 때 씁니다
- 처음 쓸 때를 위해 기본 인물 몇 명을 넣어 둡니다

## 6. 자료: 문서, 웹사이트, 웹 검색

| 기능 | 동작 | 프로바이더별 방법 |
|---|---|---|
| 문서 업로드 | PDF, Word, 텍스트, 마크다운을 올리면 글자를 뽑아 모든 참가자가 읽는 공통 자료로 넣습니다 | 내 PC에서 글자를 뽑으므로 프로바이더와 무관합니다 |
| 웹 주소 조사 | 진행자가 그 페이지를 읽고(필요하면 추가 검색) 요약, 쟁점 3~5개, 출처를 담은 브리핑을 만듭니다. 참가자는 브리핑을 놓고 토론합니다 | Claude: `web_fetch` + `web_search` 도구. P-GPT: Responses API의 웹 검색 도구. OpenAI 문서의 현재 이름은 `web_search`이고, P-GPT 스킬에서 확인된 이름은 예전 것인 `web_search_preview`입니다. 어느 쪽이 되는지는 **(미검증)** |
| 참가자 웹 검색 | 참가자가 발언 전에 스스로 검색하고, 찾은 것을 근거로 말합니다. 발언 아래에 출처가 붙습니다 | 위와 같음 |

검색 설정은 두 가지입니다: 자동(기본) / 끔. 자동에서는 참가자가 최신 사실이나 수치가 꼭 필요하다고 판단할 때만 스스로 검색하고, 대부분의 발언은 검색 없이 합니다. 발언 한 번에 검색할 수 있는 횟수도 정합니다(기본 2회).

주의할 점:

- 문서가 아주 길면 토큰 수를 미리 세어 알려 줍니다. 말없이 잘라 내지 않습니다.
- 검색 허용 여부는 토론을 시작할 때 정하고 중간에 바꾸지 않습니다. 중간에 바꾸면 캐시를 처음부터 다시 써야 합니다.
- 검색은 건당 요금이 따로 붙고 발언이 늦어집니다. 화면에는 "자료 찾는 중"으로 보입니다.
- 검색 결과는 대화 문맥에 그대로 쌓입니다. 검색을 많이 하는 긴 토론은 문맥이 빨리 커지므로 [8.5](#85-문맥이-넘칠-때-자동-압축)의 자동 압축이 필요해집니다.
- 그림과 표가 많은 PDF는 글자만 뽑으면 내용이 빠집니다. Claude에 PDF를 원본째 넘기는 방식은 나중에 추가할 수 있습니다.

## 7. LLM 연결

### 7.1 프로바이더 세 가지

`.env`의 `AITALK_PROVIDER` 값으로 고릅니다. 한 번 실행할 때 프로바이더는 하나만 씁니다. Claude 모델과 GPT 모델을 한 토론에 섞는 것은 하지 않습니다(P-GPT는 회사 OA망에서만 되기 때문입니다).

| 값 | 쓰는 곳 | 연결 방법 |
|---|---|---|
| `claude` | 집에서 개발 | 공식 Anthropic Python SDK. 키는 `.env`의 `ANTHROPIC_API_KEY` |
| `pgpt` | 회사에서 사용 | 공식 OpenAI Python SDK로 P-GPT의 `/v1` 주소에 연결. **Responses API를 상태 유지 방식으로** 씁니다(확정). 인증 토큰은 `PGPT_API_KEY`와 사번으로 만듭니다 (P-GPT 스킬 규칙) |
| `mock` | 화면 개발, 자동 시험 | API를 부르지 않고 미리 준비한 대사를 내보냅니다. 요금이 들지 않습니다 **(제안)** |

`.env`가 OS 환경 변수보다 우선합니다. 이 PC에는 다른 도구용 `OPENAI_*` 변수가 잡혀 있어서 그렇게 합니다.

P-GPT에서 Chat Completions가 아니라 Responses API를 쓰는 이유: 대화 문맥을 API가 보관하는 기능, 자동 압축, 웹 검색 도구, 추론 노력 설정이 모두 Responses 쪽에 있습니다.

### 7.2 엔진이 프로바이더에 요구하는 것

두 프로바이더는 대화 문맥을 다루는 방식이 다릅니다. Claude는 앱이 토론 기록을 매번 통째로 보내고, P-GPT는 API가 기록을 보관하고 앱은 새로 생긴 것만 보냅니다. 그래서 엔진은 "기록을 넘겨주며 부르는" 식이 아니라 **"토론 문맥"이라는 대상에 일을 시키는** 식으로 프로바이더를 부릅니다. 문맥을 실제로 어디에 두는지는 프로바이더가 알아서 합니다.

| 엔진이 시키는 일 | Claude | P-GPT |
|---|---|---|
| 모델 목록과 능력 받기 | 모델 목록 API | `/v1/models`에서 6.0 이후 모델만 |
| 토론 문맥 열기 (규칙, 전원 페르소나, 자료) | 앱 메모리에 보관 | 첫 응답을 만들고 응답 ID를 기억 |
| 발언 만들기 (글자가 흘러나옴, 검색 진행 상황과 사용량 포함) | 기록 전체 + 지시문을 보냄 | 직전 응답 ID + 지시문만 보냄 |
| 발언 확정하기 (전문 또는 끊긴 데까지) | 기록 끝에 붙임 | 그 응답을 줄기의 새 끝으로 삼음 |
| 곁가지 판단 받기 (연출자용 JSON. 문맥을 바꾸지 않음) | 같은 기록 + 질문 | 같은 응답 ID에서 갈라져 나온 호출, 저장 안 함 |
| 문맥 상태 알기 (크기, 압축됐는지) | 사용량에서 | 사용량과 압축 항목에서 |
| 문맥 다시 세우기 (서버 쪽 문맥을 잃었을 때) | 필요 없음 | 앱의 기록으로 새 줄기를 만듦 |

"발언 만들기"와 "발언 확정하기"를 나눈 이유: 다음 발언을 미리 만들어 두었다가 버리는 경우(관람자가 개입했을 때)와 끼어들기로 앞 발언을 끊는 경우가 있기 때문입니다. 만든 발언은 확정하기 전까지 문맥에 들어가지 않습니다.

`mock` 프로바이더도 이 일곱 가지를 그대로 흉내 냅니다. 응답 ID와 압축 신호까지 흉내 내므로, 집에서 P-GPT 없이도 엔진의 상태 유지 처리를 시험할 수 있습니다.

### 7.3 모델과 추론 노력

- **기본: 단일 모델.** 참가자, 진행자, 연출자가 모두 같은 모델과 같은 추론 노력을 씁니다. 캐시 할인이 가장 큽니다.
- **고급: 화자별 설정.** 참가자마다 모델과 추론 노력을 따로 고릅니다. 화면에 "캐시 할인이 줄어든다"는 안내를 띄웁니다.
- 모델 목록은 프로바이더에서 실시간으로 받아 옵니다.

지금 `.env`의 키로 확인한 결과 Claude 모델 15개가 보입니다. 현재 세대 모델의 요금은 아래와 같습니다 (100만 토큰당, 2026-11-03 기준 자료).

| 모델 | 입력 | 캐시 읽기 | 출력 |
|---|---|---|---|
| Claude Fable 5.2 | $8 | $0.20 | $40 |
| Claude Opus 5.5 | $4 | $0.20 | $20 |
| Claude Sonnet 5.5 | $2 | $0.10 | $10 |
| Claude Haiku 5.5 | $0.10 | $0.01 | $0.50 |

캐시에 처음 쓸 때는 입력 요금의 1.25배가 듭니다.

**Claude 기본값(확정)**: 시험하는 동안은 Claude Haiku 5.5, 추론 노력 `low`입니다. 싸고 빨라서 여러 번 돌려 보기에 맞습니다. 품질을 보려면 고급 설정에서 Opus 5.5로 바꿉니다. 추론 노력은 `low`~`max` 다섯 단계에서 고를 수 있습니다.

**P-GPT 모델(확정)**: `gpt-6-luna`, `gpt-6.1-sol`, `gpt-6.1-terra` 세 가지를 지원합니다. 기본은 `gpt-6-luna`, 추론 노력 `medium`입니다. ("6-luna-medium"을 모델 `gpt-6-luna`에 추론 노력 `medium`으로 읽었습니다. 다르면 알려 주세요.)

- 이 세 모델을 P-GPT의 `/v1/models`와 맞춰 보고, 있는 것만 목록에 올립니다. 목록을 받지 못하면 세 모델을 그대로 보여 줍니다.
- P-GPT가 이 세 모델을 실제로 제공하는지는 **(미검증)**입니다. 요금과 추론 노력 단계는 OpenAI 공식 문서의 값입니다.

| 모델 | 입력 | 캐시 읽기 | 출력 | 추론 노력 |
|---|---|---|---|---|
| `gpt-6.1-sol` | $2 | 입력의 5% | $10 | low ~ max로 잡음 (문서 미확인) |
| `gpt-6.1-terra` | $1 | 입력의 5% | $5 | low ~ max로 잡음 (문서 미확인) |
| `gpt-6-luna` (기본) | $0.1 | $0.01 | $0.5 | none, low, medium(기본), high, xhigh, max |

요금은 OpenAI 공개 요금(100만 토큰당)이며 회사 안에서의 정산과는 다를 수 있습니다. 캐시에 처음 쓸 때는 Claude와 같이 입력 요금의 1.25배가 듭니다. `gpt-6-luna`는 문맥 창이 105만 토큰이고, 입력이 27.2만 토큰을 넘는 요청은 입력 요금이 2배가 됩니다.

추론 노력 설정(`reasoning.effort`)이 P-GPT에서 그대로 통하는지는 **(미검증)**입니다.

### 7.4 관찰을 돕는 기능 (제안)

성능이 다른 AI를 비교해 보려는 목적에 맞춰 넣으면 좋을 것들입니다.

- **모델 배지**: 참가자 타일에 모델 이름과 추론 노력을 표시합니다. 끄고 켤 수 있습니다.
- **블라인드 모드**: 토론 중에는 모델을 가리고, 끝난 뒤에 공개합니다.
- **생각 보기**: Claude는 발언 전에 한 생각의 요약을 받을 수 있습니다. 발언 옆에 접어 두고 펼쳐 볼 수 있게 합니다.
- **사용량 표시**: 화자별 토큰, 캐시 적중률, 예상 비용을 보여 줍니다.

## 8. 문맥 관리와 캐시

단일 모델을 권장하는 이유가 이 부분이라 따로 적습니다. 8.1~8.3은 원리와 Claude 쪽 방식이고, 8.4~8.5는 P-GPT의 상태 유지 방식과 자동 압축입니다.

| | Claude | P-GPT |
|---|---|---|
| 토론 기록을 누가 들고 있나 | 앱. 호출마다 통째로 보냅니다 | API 서버. 앱은 직전 응답 ID와 새 지시문만 보냅니다 |
| 캐시 | 앱이 캐시 지점을 표시합니다 | 자동 |
| 문맥이 넘칠 때 | 서버 압축(베타)을 켜고, 압축 결과를 앱이 다시 보냅니다 | 서버가 자동 압축하고 알아서 이어 갑니다 |

### 8.1 원리

캐시는 **요청의 앞부분이 직전 요청과 한 글자도 다르지 않을 때** 그 부분만 할인해 줍니다. 그래서 요청을 다음 순서로 조립합니다.

```
[앞부분: 누가 말하든 똑같음]
  ① 토론 규칙, 진행 형식
  ② 참가자 전원의 페르소나
  ③ 자료 (문서 내용, 브리핑)
  ④ 지금까지의 토론 기록 (발언이 끝날 때마다 뒤에 하나씩 붙음)
──────── 여기까지 캐시 ────────
[꼬리: 호출마다 다름]
  ⑤ "이번에는 ○○로서 말하세요. △△에 반박, 2~4문장." (또는 연출자용 질문)
```

핵심은 ④입니다. 보통의 챗봇처럼 "내 말은 assistant, 남의 말은 user"로 넣으면 화자마다 기록 모양이 달라져 캐시를 못 씁니다. 그래서 기록을 **"【이름】 발언" 형식의 중립적인 대본**으로 넣고, 누구로서 말할지는 맨 끝 꼬리에서만 지정합니다.

이렇게 하면 발언자 호출과 연출자 호출이 모두 같은 앞부분을 공유합니다. 매 호출은 직전까지의 내용을 캐시로 읽고, 새로 붙은 발언 하나만 새로 씁니다.

Claude에서는 앱이 이 조립을 호출마다 직접 합니다. P-GPT에서는 ①~④를 서버가 보관하고 앱은 ⑤만 보내지만, 서버 안에서 만들어지는 순서는 같습니다([8.4](#84-p-gpt-api가-문맥을-보관하는-방식)).

### 8.2 얼마나 아끼나 (추정)

실측이 아니라 가정을 둔 계산입니다. 만든 뒤 실제 사용량으로 바꿔 적겠습니다.

가정: Claude Opus 5.5, 앞부분 3,000토큰, 발언 하나에 250토큰, 40턴, 턴마다 호출 2번(연출자와 발언자).

| | 입력 토큰 처리 | 입력 비용 |
|---|---|---|
| 캐시 없이 | 약 63만 토큰을 정가로 | 약 $2.5 |
| 캐시 사용 | 약 63만 토큰은 캐시 읽기, 1.3만 토큰만 새로 쓰기 | 약 $0.2 |

입력 비용이 10분의 1 아래로 내려갑니다. 출력 비용(이 가정에서 약 $0.4와 생각 토큰)은 캐시와 무관하게 그대로 듭니다.

**실측 (2026-11-17, Claude Opus 5.5, `low`).** 참가자 4명과 진행자, 18턴 토론 한 번의 결과입니다. 입력 토큰 20.4만 가운데 81%를 캐시에서 읽었고, 전체 비용은 약 $0.41(참가자 생성 제외, 요약 카드 포함), 토론에 걸린 시간은 약 3분이었습니다. 발언 하나는 2~3초에 만들어졌습니다. 발언자 호출과 연출자 호출은 캐시 줄기가 따로 생겼습니다(연출자 쪽은 JSON 틀이 앞부분에 들어가기 때문). 둘 다 자기 줄기 안에서는 캐시가 맞습니다.

### 8.3 캐시가 깨지는 경우와 대응 (Claude)

| 경우 | 영향 | 대응 |
|---|---|---|
| 화자마다 모델이 다름 | 캐시는 모델별로 따로입니다. 각 모델은 자기가 마지막으로 말한 뒤에 쌓인 발언을 전부 새로 씁니다 | 고급 설정으로 두고 안내를 띄웁니다. 그래도 자기 차례가 다시 올 때까지의 앞부분은 캐시로 읽습니다 |
| 화자마다 추론 노력이 다름 | 같은 모델이어도 대화 기록 캐시가 깨집니다 | Claude에는 캐시를 유지한 채 노력을 바꾸는 방법(베타)이 있어 적용해 봅니다. 효과는 실측으로 확인합니다 |
| 웹 검색을 중간에 켜고 끔 | 앞부분 전체를 다시 씁니다 | 시작할 때 정하고 고정합니다 |
| 5분 넘게 멈춰 둠 | 캐시가 만료됩니다 | 일시정지 중에는 4분마다 출력 없는 요청을 보내 캐시를 살려 둡니다. 최대 30분까지 |
| 끼어들기로 앞 발언을 끊음 | 마지막 발언 하나만 다시 씁니다 | 영향이 작아 그대로 둡니다 |

만든 뒤에는 응답의 사용량 항목(`cache_read_input_tokens`)으로 캐시가 실제로 맞는지 매번 확인하고, 자동 시험에도 넣습니다. 캐시는 깨져도 오류 없이 요금만 오르기 때문입니다.

### 8.4 P-GPT: API가 문맥을 보관하는 방식

요구(확정): P-GPT는 Responses API를 쓰고, 대화 문맥을 API 쪽에서 관리하며, 문맥이 넘치면 자동으로 압축합니다.

아래 파라미터 이름은 OpenAI 공식 문서(2026-11-17 확인)와 P-GPT 스킬의 확인된 패턴에서 가져왔습니다. P-GPT에서 실제로 되는지는 [14번](#14-아직-검증하지-못한-것)의 항목으로 회사에서 확인합니다.

**기본 동작.** 모든 응답을 `store=True`로 만들고, 다음 호출에서 `previous_response_id`로 직전 응답을 가리킵니다. 서버가 그때까지의 입력과 출력을 이어 붙여 문맥으로 쓰므로 앱은 새 지시문만 보냅니다. 이 방식은 P-GPT 스킬에 "확인된 패턴"으로 올라 있습니다.

**토론 줄기.** 발언자 호출만 한 줄로 이어 갑니다.

```
[응답 1]  입력: 토론 규칙 + 전원 페르소나 + 자료 + 지시문 "【다음 발언: A】 모두발언"   → 출력: 발언 1
[응답 2]  가리킴: 응답 1   입력: 지시문 "【다음 발언: B】 A에 반박, 2~4문장"            → 출력: 발언 2
[응답 3]  가리킴: 응답 2   입력: 지시문 …                                             → 출력: 발언 3
             └ [연출자 곁가지]  가리킴: 응답 3   입력: "다음에 누가 말할지 판단"   저장 안 함, 줄기에 잇지 않음
```

| 상황 | 처리 |
|---|---|
| 누가 한 말인지 | 지시문에 화자 이름이 들어가므로 서버에 쌓인 기록이 그대로 대본이 됩니다. 8.1의 "중립적인 대본"과 같은 모양입니다 |
| 규칙, 페르소나, 자료 | 응답 1의 입력에 넣어 줄기에 남깁니다. `instructions` 칸은 요청 맨 앞에 놓여 내용이 바뀌면 캐시가 처음부터 깨지므로, 비우거나 고정 문구만 둡니다 |
| 연출자 호출 | 마지막 발언의 응답 ID에서 갈라져 나온 곁가지로 부르고 `store=False`로 둡니다. 줄기에는 흔적이 남지 않고, 앞부분 캐시는 같이 씁니다 |
| 미리 만든 발언을 버릴 때 | 그 응답을 줄기에 잇지 않으면 됩니다 |
| 끼어들기로 앞 발언을 끊을 때 | 끊긴 발언의 응답은 줄기에 잇지 않습니다. 그 앞 응답을 가리키고, "끊긴 데까지의 발언"을 입력 항목으로 넣은 뒤 이어 갑니다 |
| 연출자의 JSON 틀, 화자별 추론 노력 | 요청 설정(`text.format`, `reasoning.effort`)을 바꾸면 캐시가 깨집니다. GPT-6 이후에는 `configuration_update` 입력 항목으로 앞부분을 건드리지 않고 바꿀 수 있어 이것을 씁니다 **(미검증)**. 안 되면 연출자는 글로 받아 파싱하고, 화자별 노력은 캐시를 포기합니다 |
| 화자별 모델 | 줄기 중간에 모델만 바꿔 부릅니다 **(미검증)**. 안 되면 모델마다 줄기를 따로 두고, 다른 모델이 한 발언을 입력 항목으로 넣어 줍니다 |

**요금은 줄지 않습니다.** 서버가 문맥을 보관해도 줄기의 앞 내용은 호출마다 입력 토큰으로 계산됩니다(OpenAI 문서). 절약은 캐시에서 나옵니다. 상태 유지의 이점은 요금이 아니라 세 가지입니다: 매번 보내는 양이 작고, 모델이 앞에서 한 추론이 서버에 남아 이어지며, 문맥 압축을 서버에 맡길 수 있습니다.

**캐시.** GPT-5.6 이후 모델은 앞부분이 같으면 자동으로 캐시를 씁니다. 최소 1,024토큰, 기본 30분 유지, 쓰기는 입력 요금의 1.25배, 읽기는 10%(GPT-6.1 Sol·Terra는 5%)입니다. 실제로 맞았는지는 사용량의 `input_tokens_details.cached_tokens`와 `cache_write_tokens`로 확인합니다. 모델, 도구 목록, 출력 형식, 추론 노력, 압축 설정이 바뀌면 캐시가 깨지므로 토론을 시작할 때 정하고 고정합니다. 유지 시간이 30분이라 8.3의 "4분마다 살려 두기"는 Claude에서만 합니다.

**`conversation`(Conversations API)이 아니라 `previous_response_id`를 쓰는 이유.** 대화 객체는 한 줄로만 쌓여서 연출자 호출과 버린 발언까지 섞여 들어갑니다. 응답 ID 방식은 같은 지점에서 여러 갈래로 갈라질 수 있어 이 설계에 맞습니다. 한 응답에서 두 갈래 이상을 만들 수 있는지는 OpenAI 문서에서 명시된 문장을 찾지 못해 **(미검증)**으로 둡니다. 안 되면 연출자 호출을 줄기에 넣고 그만큼의 토큰을 감수합니다.

**앱의 기록이 원본입니다.** 화면, 저장, 다시 보기는 모두 앱이 가진 기록으로 합니다. 서버의 문맥은 모델의 기억일 뿐입니다. 서버 보관은 OpenAI 기준 30일이고 P-GPT의 보관 기간은 **(미검증)**입니다. 응답 ID를 서버가 찾지 못하면 앱의 기록으로 새 줄기를 만들어 이어 갑니다. 그래서 며칠 전에 멈춘 토론도 이어 할 수 있습니다.

**알아 둘 점.** `store=True`이므로 올린 문서와 토론 내용이 P-GPT 서버에 보관됩니다. 새 토론 화면에 이 사실을 한 줄로 알립니다.

### 8.5 문맥이 넘칠 때: 자동 압축

**P-GPT.** 모든 요청에 `context_management=[{"type": "compaction", "compact_threshold": N}]`을 붙입니다. 문맥이 N토큰을 넘으면 서버가 앞부분을 스스로 압축하고 줄기는 그대로 이어집니다. `previous_response_id`로 이어 가는 한 앱이 따로 할 일은 없습니다. 압축된 내용은 암호화된 항목이라 사람이 읽을 수 없습니다.

| 항목 | 내용 |
|---|---|
| 압축 기준 N | 기본 20만 토큰 **(제안)**. `gpt-6-luna`는 입력이 27.2만 토큰을 넘으면 요금이 2배가 되므로 그 아래로 잡았습니다. 설정에서 바꿀 수 있고, 토론 중에는 고정합니다(바꾸면 캐시가 깨집니다) |
| 언제 작동하나 | 보통 토론(30턴, 약 1.5만 토큰)에서는 닿지 않습니다. 긴 문서를 올렸거나, 검색을 많이 하거나, 수백 턴을 돌릴 때 작동합니다 |
| 압축 뒤 보정 **(제안)** | 압축은 맨 앞의 규칙과 페르소나도 함께 줄이므로 말투와 입장이 흐려질 수 있습니다. 응답에서 압축 항목을 발견하면 다음 지시문 앞에 규칙과 전원 페르소나를 다시 넣습니다 |
| 화면 표시 | 타임라인에 "문맥 압축" 표시를 찍고, 사용량 패널에 횟수를 보여 줍니다 |
| 캐시 | 압축 직후 한 번은 앞부분을 새로 씁니다 |

P-GPT가 `context_management`를 받지 않을 때의 대안은 순서대로 두 가지입니다.

1. 앱이 기준을 넘었을 때 `/responses/compact`를 직접 불러 압축된 문맥을 받고, 그것으로 새 줄기를 시작합니다.
2. 그것도 안 되면 앱이 모델에게 앞부분 요약을 시켜 새 줄기를 만듭니다: 규칙 + 페르소나 + 자료 브리핑 + 앞 토론 요약 + 최근 발언 몇 개의 원문.

어느 경우에도 앞부분을 말없이 잘라 버리는 방식은 쓰지 않습니다.

**Claude.** 요청하신 것은 P-GPT지만, 같은 문제가 Claude에서도 생기므로 같이 넣었습니다. 2판에서는 Claude의 서버 압축 기능(베타)을 쓰겠다고 적었는데, 만들면서 바꿨습니다. 서버 압축은 주고받은 메시지를 줄이는 기능이고, 이 프로그램은 토론 기록 전체를 한 덩어리 대본으로 보내기 때문에 맞지 않습니다. 그래서 Claude에서는 입력이 기준(기본 15만 토큰)을 넘으면 앱이 모델에게 앞부분 요약을 시켜, 최근 발언 6개만 원문으로 남기고 나머지를 요약 한 줄로 바꿉니다. 엔진은 두 프로바이더에서 같은 "압축됨" 신호를 받아 화면 표시를 똑같이 합니다.

### 8.6 이 방식의 한계

- 참가자 전원의 페르소나가 공통 앞부분에 들어가므로, 각 참가자는 서로의 인물 설명을 읽을 수 있습니다.
- **숨은 속내.** Claude에서는 공통 앞부분에 넣지 않고 그 사람 차례의 꼬리에만 넣어 남에게 보이지 않게 합니다. P-GPT에서는 보낸 지시문이 줄기에 남으므로 이 방법이 통하지 않습니다. 그래서 P-GPT에서는 숨은 속내를 기본으로 끄고, 켜면 "다른 참가자가 알아챌 수 있다"는 안내를 띄웁니다.
- **압축 뒤의 기억.** 압축된 뒤에는 모델이 앞부분 발언을 원문 그대로 기억하지 못합니다. "아까 ○○ 님이 하신 말"을 정확히 인용하는 일이 줄어들 수 있습니다. 화면과 기록은 앱이 가진 원문을 쓰므로 영향이 없습니다.

| 봇 | 화면 얼굴을 가진 로봇 | 눈의 모양과 기울기, 입 막대의 높낮이 | 6 |
| 얼굴 | 도형으로 만든 얼굴 | 눈썹 각도, 눈 크기, 입 모양, 볼 | 6 |
| 정령 | 고리가 도는 빛의 핵 | 회전 속도, 핵의 박동, 가시와 파동 | 6 |
| 문장 | 문양을 담은 금빛 틀 | 틀의 회전과 박동, 문양의 기울기와 떨림 | 15 |

감정은 여덟 가지(평온, 수긍, 못마땅, 격앙, 궁금, 놀람, 웃음, 고민)이고, 상태는 여섯 가지(쉬는 중, 듣는 중, 발언 준비, 말하는 중, 검색 중, 말이 끊김)입니다. 세트 4 × 감정 8의 움직임이 프리셋으로 들어 있고, 여기에 상태별 움직임이 겹쳐집니다.

- **감정은 어디서 오나.** 발언이 끝날 때마다 연출자가 참가자 전원의 감정을 함께 정합니다(3.4). 듣는 사람들의 아바타가 그 감정으로 바뀌고, 그 사람이 다음에 말하게 되면 그 감정으로 말합니다.
- **말할 때.** 봇은 입 막대가 음성 파형처럼 뛰고, 얼굴은 입이 움직이고, 정령은 파동이 퍼지고, 문장은 틀이 박동합니다. 격앙된 상태에서는 더 빠르고 크게 움직입니다.
- **감정 표시.** 아바타 오른쪽 위에 작은 아이콘(Lucide)이 감정을 한 번 더 알려 줍니다. 발언 의지가 8점 이상이면 손 아이콘이 뜹니다.
- **고르기.** 새 토론 화면에서 세트를 고르면 참가자에게 서로 다른 아바타가 배정됩니다. "섞어서"를 고르면 네 세트가 고르게 나옵니다. 인물마다 따로 바꿀 수도 있습니다.
- **미리 보기.** 페르소나 편집 화면에서 감정을 눌러 움직임을 볼 수 있고, 설정 화면에 세트 × 감정 전체 표가 있습니다.

아바타 모양은 원과 사각형 같은 기본 도형으로 조립했습니다. 아이콘(문장 세트의 문양, 감정 표시)은 전역 지침대로 Lucide에서 가져왔습니다.

## 10. 기술 구성

nova-agent와 같은 방식입니다.

```
AI-Talk/
  apps/
    server/        Python 3.13, FastAPI. 토론 엔진, 프로바이더, 저장
      providers/   claude.py, pgpt.py, mock.py
    web/           Vite + TypeScript (프레임워크 없음), Lucide
  data/            페르소나, 토론 기록, 올린 문서 (git 제외)
  presets/         기본 인물 (git에 포함)
  docs/            이 문서
  scripts/         P-GPT 점검 스크립트 등
  .env             개인 키 (git 제외)   .env.example   run.bat
```

- **서버와 화면의 통신**: 토론 진행은 서버가 화면으로 계속 흘려보내고(SSE), 멈춤·속도·개입 같은 조작은 화면이 서버로 따로 보냅니다.
- **저장**: 페르소나 보관함과 토론 기록(발언, 이벤트, 요약, 회의록)을 SQLite 파일 하나(`data/aitalk.db`)에 둡니다. 예전 버전의 JSON 파일이 있으면 처음 한 번 옮겨 옵니다. 진행 설정은 사람마다 다르므로 각자의 브라우저에 기억합니다. 토론 기록은 화면에 내보낸 순서와 시간을 그대로 담아 다시 보기에 씁니다. P-GPT에서는 줄기의 마지막 응답 ID도 함께 저장해, 프로그램을 껐다 켜도 같은 서버 문맥에서 이어 갑니다.
- **프로바이더 구조**: 엔진은 [7.2](#72-엔진이-프로바이더에-요구하는-것)의 일곱 가지 일만 시킵니다. 문맥을 앱이 들고 있는지(Claude) 서버가 들고 있는지(P-GPT)는 프로바이더 안에 숨깁니다.
- **접속 범위**: 기본은 내 PC에서만 접속됩니다(127.0.0.1). `.env`에 `AITALK_HOST=0.0.0.0`을 두면 같은 망의 다른 PC에서 `http://내IP:포트`로 들어올 수 있습니다. 로그인은 없고, `AITALK_ACCESS_CODE`를 정해 두면 다른 PC에는 접속 코드를 묻습니다. 코드를 정하지 않으면 같은 망의 누구나 들어와 내 AI 키로 토론을 돌릴 수 있으므로, 망에 열 때는 코드를 정하기를 권합니다.
- **Claude 호출**: 안전 장치가 요청을 거절하면 다른 모델로 넘기는 설정(`fallbacks`)을 기본으로 켭니다.
- **오류가 났을 때**: API 호출이 실패하면 두 번까지 다시 시도합니다. 그래도 안 되면 토론을 일시정지 상태로 두고 이유를 보여 줍니다. 그때까지의 기록은 남아 있고, "이어 하기"를 누르면 그 자리에서 다시 시작합니다.
- **비용 안전장치**: 턴 수와 시간 제한 가운데 하나는 반드시 켜져 있어야 시작됩니다. 토론이 끝없이 돌지 않게 하기 위해서입니다.

## 12. 만드는 순서

각 단계가 끝날 때마다 실제로 돌려서 확인하고 커밋합니다.

1. **뼈대**: 서버, Claude와 mock 프로바이더, 토론 엔진(순차와 자유), 기본 무대 화면. 캐시가 실제로 맞는지 사용량으로 확인합니다. 프로바이더 구조는 처음부터 [7.2](#72-엔진이-프로바이더에-요구하는-것)의 "토론 문맥" 방식으로 잡고, mock이 응답 ID·곁가지·압축 신호를 흉내 내게 해서 상태 유지 처리를 집에서 시험합니다.
2. **페르소나**: 자동 생성, 보관함, 관리 메뉴.
3. **자료**: 문서 업로드, 웹 주소 조사, 참가자 웹 검색.
4. **실감과 디자인**: 속도·뜸·끼어들기 다듬기, 모션, 참고 사이트 수준의 마감.
5. **기록**: 저장, 다시 보기, 내보내기, 사용량 표시.
6. **P-GPT**: 상태 유지 방식의 프로바이더를 만들고, 회사에서 돌릴 점검 스크립트를 함께 둡니다. 점검 스크립트는 [14번](#14-아직-검증하지-못한-것)의 항목을 하나씩 실제로 불러 보고 되는 것과 안 되는 것을 표로 내놓습니다. 프로바이더는 그 결과에 따라 대안으로 넘어가도록 만듭니다.

## 14. 아직 검증하지 못한 것

P-GPT는 회사 OA망에서만 되므로 집에서는 확인할 수 없습니다. 6단계에서 만들 점검 스크립트를 회사에서 한 번 돌려 아래를 확인합니다.

| 항목 | 확인할 것 | 안 될 때의 대안 |
|---|---|---|
| 모델 목록 | `/v1/models`에 `gpt-6-luna`, `gpt-6.1-sol`, `gpt-6.1-terra`가 있는지 | 있는 것만 목록에 올림. 하나도 없으면 알려 드리고 정합니다 |
| Responses 스트리밍 | 발언이 흘러나오는지 (스킬에서 확인된 패턴) | 다 받은 뒤 한 번에 표시 |
| 상태 유지 | `store=True` + `previous_response_id`로 이어지는지 (스킬에서 확인된 패턴), 6.x 모델에서도 되는지 | 앱이 기록을 매번 보내는 방식으로 전환 |
| 곁가지 | 한 응답 ID에서 두 갈래로 부를 수 있는지, 곁가지를 `store=False`로 둘 수 있는지 | 연출자 호출도 줄기에 넣음 |
| 끊긴 발언 넣기 | 앞 응답을 가리키면서 발언 문장을 입력 항목으로 넣을 수 있는지 | 다음 지시문에 "앞 발언은 ○○까지만 말하고 끊겼다"고 적음 |
| 자동 압축 | `context_management`의 `compaction`을 받는지, 압축 항목이 응답에 나오는지 | `/responses/compact` 직접 호출 → 앱이 요약해 새 줄기 ([8.5](#85-문맥이-넘칠-때-자동-압축)) |
| 중간 설정 변경 | `configuration_update` 입력 항목이 되는지 | 연출자는 글로 받아 파싱, 화자별 노력은 캐시 포기 |
| 줄기 중 모델 변경 | 줄기 중간에 `model`만 바꿔 부를 수 있는지 | 모델마다 줄기를 따로 둠 |
| 서버 보관 기간 | 저장된 응답이 며칠 뒤에도 남아 있는지 | 응답 ID를 못 찾으면 앱 기록으로 새 줄기 |
| 추론 노력 | `reasoning.effort` 설정이 통하는지, 어떤 단계가 있는지 | 설정 항목을 숨김 |
| 웹 검색 | `web_search`와 `web_search_preview` 가운데 무엇이 되는지, 특정 주소를 읽을 수 있는지 | 서버가 페이지를 직접 받아 글자만 넘김 |
| 캐시 | 사용량에 `cached_tokens`, `cache_write_tokens`가 나오는지 | 사용량 표시에서 캐시 항목을 뺌 |
| JSON 틀 | 정해진 틀의 JSON 출력이 되는지 (스킬에서 확인된 패턴) | 글로 받아 파싱 |
| 사내 인터넷 | 서버 PC에서 외부 웹 페이지를 직접 받을 수 있는지 | 웹 주소 조사를 프로바이더 도구에만 맡김 |

OpenAI 공식 문서에서 찾지 못해 구현할 때 다시 확인할 것:

- `instructions`가 `previous_response_id`로 이어진 다음 응답에 따라오는지. 설계는 `instructions`를 비우거나 고정하므로 어느 쪽이든 동작합니다.
- 압축 항목이 스트리밍에서 어떤 이벤트로 오는지.
- `gpt-6.1-sol`, `gpt-6.1-terra`, `gpt-6-sol`의 추론 노력 단계와 요금 가운데 표에 "문서 미확인"으로 적은 칸.

Claude 쪽에서 실측으로 확인할 것:

- 연출자 호출과 발언자 호출이 같은 캐시를 실제로 공유하는지. JSON 틀을 지정하면 캐시가 갈릴 수 있습니다. 갈리면 연출자는 글로 받아 파싱합니다.
- 화자별로 추론 노력이 다를 때 캐시를 유지하는 방법이 기대대로 동작하는지.

### 16.1 다음 발언을 만드는 시점

토큰을 미리 써 두지 않기 위한 규칙입니다.

1. 화면에 나오는 발언보다 **한 발언만** 앞서 만듭니다. 그 이상은 만들지 않습니다.
2. 연출자는 앞 발언이 화면에 **30%쯤 나왔을 때** 부릅니다. 끼어들기로 정해지면 말을 끊을 자리가 남아 있어야 하기 때문입니다. 듣는 사람들의 아바타가 이때 반응합니다.
3. 다음 발언은 앞 발언의 **남은 재생 시간이 발언 하나를 만드는 데 걸리는 시간과 비슷해졌을 때** 만들기 시작합니다. 걸리는 시간은 최근 호출들로 계속 다시 잽니다. 끼어들기는 곧 말을 끊으므로 바로 만듭니다.
4. 멈춤 상태에서는 새 호출을 시작하지 않습니다.
5. 보는 사람이 하나도 없으면 12초 뒤 토론을 멈춥니다. 다시 열면 이어 갑니다.

그래서 보다가 창을 닫으면, 버려지는 것은 많아야 연출자 호출 한 번과 발언 하나입니다.

### 16.2 웹 검색 자동 모드에서 달라지는 것

- 검색 도구가 있으면 모델이 "검색해 보겠습니다" 같은 말을 먼저 하는 일이 있어, 검색 전에 한 말은 버리고 검색 뒤의 말만 발언으로 씁니다. 이를 위해 Claude에서는 글을 덩어리 단위로 받습니다. 화면에 나오는 박자는 서버가 정하므로 보는 쪽에서는 차이가 없습니다.
- 연출자 호출에는 검색 도구를 넣지 않습니다. JSON 틀은 검색 인용과 함께 쓸 수 없기 때문입니다.
- Claude Haiku는 예전 버전의 검색 도구를 씁니다.

### 16.3 바꾼 뒤 확인한 것과 못한 것

확인한 것:

- **자동 시험 15개 통과.** 엔진 9개(위의 시점 규칙을 넣은 뒤 다시), 저장소 3개(처음 실행 때 기본 인물 넣기, 넣고 고치고 지우기, 회의록을 기록에 더하기), 접속 코드와 회의록 API 3개.
- **Claude Haiku 5.5로 실제 토론 한 번.** 컨셉("심야 라디오 토론")을 넣고 참가자 4명, 16턴. 재생에 2분 37초, 비용 약 $0.013, 입력의 84%를 캐시에서 읽었습니다. 앞서 Opus 5.5로 돌린 18턴 토론은 약 $0.41이었습니다. 이 토론에서는 참가자들이 검색이 필요 없다고 판단해 검색하지 않았습니다.
- **Haiku의 웹 검색.** 검색이 꼭 필요한 지시를 따로 주어 확인했습니다. 검색이 실행됐고, 검색 전에 한 말은 발언에 섞이지 않았습니다. 다만 그때 모델이 인용 표시를 붙이지 않아 출처가 비어 나왔습니다. 그래서 인용이 없으면 찾아본 결과의 앞쪽 3개를 출처로 보여 주게 고쳤는데, 이 보강은 다시 돌려 확인하지 못했습니다.
- **회의록.** 위 토론으로 실제로 만들었습니다. 안건 5개, 쟁점 5개마다 누가 무엇을 말했는지, 합의 사항 4개, 미결 사항 3개, 후속 조치 0개가 정리됐습니다.
- **복사.** 회의록과 대화 전체가 마크다운 한 덩어리(약 8천 자)로 만들어지는 것을 확인했습니다.
- **기존 기록 옮기기.** 예전 JSON 파일의 인물 8명과 토론 3개가 SQLite로 옮겨졌습니다.

확인하지 못한 것:

- **다른 PC에서 실제로 접속하기.** 접속 코드 확인은 자동 시험으로 했지만, `AITALK_HOST=0.0.0.0`으로 켜고 다른 PC에서 들어와 보지는 못했습니다. 방화벽 설정은 PC마다 다릅니다.
- **보는 사람이 없을 때 멈추는 동작.** 코드는 넣었지만 실제로 창을 닫았다 열어 보는 확인은 하지 못했습니다.
- **글자가 흘러나오는 모습과 오른쪽 참가자 칸의 움직임.** 브라우저 창이 숨겨진 상태라 정지 화면과 수치로만 확인했습니다.
- P-GPT는 여전히 한 번도 실행하지 못했습니다.
